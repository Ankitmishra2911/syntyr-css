# Selective builds and unused CSS

Syntyr's default CSS distributions remain deterministic, standards-based and usable
without a compiler or JavaScript. Size is **measured, not capped**: there are no
hard CSS bundle size budgets.

For applications that need fewer shipped styles, the Python standard-library
builder supports an **optional application-specific output**. It eliminates
unused *modules* and unselected *named palettes*. It deliberately preserves
all selectors and interaction states inside any included module.

## Explicit selection

```sh
python3 scripts/build.py \
  --components buttons,forms,data \
  --modules semantic,presets \
  --themes corporate \
  --output public/css/application.css \
  --report public/css/application.report.json
```

Available components: `layout`, `typography`, `buttons`, `forms`, `overlays`,
`data`, `patterns`.

Optional modules: `semantic`, `recipes`, `geometry`, `effects`,
`application`, `presets`, `utilities`.

Named themes: `grid`, `noir`, `studio`, `industrial`, `terminal`,
`corporate`, `minimal`. The default Grid palette is always included so a
`.syn-root` without a theme attribute still has meaningful colors. The
`--themes` option removes other unused palette rules.

`--output` refuses to replace canonical committed `dist/` artifacts.
Standard `python3 scripts/build.py` and `--check` remain unchanged.

## Conservative application scanning

```sh
python3 scripts/build.py \
  --scan ./app/templates \
  --scan ./app/components \
  --themes corporate,studio \
  --safelist syn-button--primary,syn-dialog \
  --output public/css/application.css \
  --report public/css/application.report.json
```

The scanner looks for literal `syn-*` classes in typical HTML, JS/TS, React,
Vue, Svelte, Astro, Go, Rust, PHP, Python and template sources. Recognized
classes pull in the *entire* component/module stylesheet: active, hover,
focus, invalid, loading, responsive and forced-colors states are preserved.
`data-syn-density` or `data-syn-geometry` references pull in presets.

If class names are assembled dynamically, generated by HTMX fragments not in
the scanned tree, injected by server routes, or constructed from user data,
**use explicit `--components` / `--modules` and `--safelist`**. A static scan
cannot infer unseen runtime classes. Scan complete application sources,
including server-rendered fragments and lazy-loaded routes. Review its JSON
`included_sources` list and test actual pages before shipping.

## Selector-level elimination (external, optional)

Application-specific CSS purgers can remove individual unused selectors after
Syntyr's selective build. Use a parser that understands CSS nesting and
`@layer`, `@container`, native state selectors, and `@media`. Preserve
relevant `:hover`, `:focus-visible`, `:user-invalid`, `[aria-*]`, native
`dialog`/`popover`, dynamically generated class names, and CSS custom
properties. With HTMX or server fragments, include the returned markup and
all reachable states in the content input. Incorrect selector pruning can
cause production-only visual defects; keep it opt-in and browser-tested.

Syntyr does **not** ship a homegrown CSS parser or force npm, a runtime
JavaScript framework, or a third-party purger on consumers. For small sites,
ordinary modular distribution is often enough.

## Runtime and compatibility

Built-in components use native CSS nesting to remain scoped to descendants
of `.syn-root`, with low specificity via `:where()`. Theme palettes use CSS
custom properties and `color-mix()`. Opt-in auto-sizing textareas use
`field-sizing: content` under `@supports` with standard sizing as fallback.
Verify your project's browser support matrix before targeting old browser
versions. The stylesheet never adds JavaScript.
